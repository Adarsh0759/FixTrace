# FixTrace-RAG — Project Decisions Log

This file is the single source of truth for *why* the project is built the way it is. Code and READMEs explain *what* exists; this file explains *why it exists this way and not another way*. Update it whenever a decision is made, reversed, or revisited — do not let it go stale.

Each entry follows the same shape: **Decision → Reason → Alternatives considered → Risk if wrong.**

---

## 1. Core framing decisions

### 1.1 Separate "software quality" from "research quality"
**Decision:** Treat the working web app and the research contribution as two different deliverables with two different success criteria.
**Reason:** A chatbot that returns confident-looking JSON is not evidence that version-aware retrieval or claim verification *improves* anything. The research deliverable is a measured delta (or a documented null result) on a frozen evaluation set, not the existence of the app.
**Alternatives considered:** Ship the app and treat a few anecdotal examples as "proof." Rejected — anecdotes don't survive scrutiny in a portfolio/paper context, and the whole point of the project is to demonstrate rigor.
**Risk if wrong:** Looks like a CRUD app with an LLM bolted on, not a research artifact.

### 1.2 Research question is a hypothesis to test, not a result to assume
**Decision:** The primary research question — *does version-aware retrieval + claim-level verification reduce unsupported recommendations without substantially hurting answer coverage?* — is written and frozen before most of the system exists.
**Reason:** Prevents post-hoc rationalization ("we built X, so X must help"). Forces a falsifiable claim.
**How to apply:** If B4/B5 underperform B2/B3 on the frozen test set, that is a reportable finding, not a bug to hide.

### 1.3 Small, trustworthy dataset over large synthetic one
**Decision:** Target ~150–250 manually reviewed cases, starting with a 20–30 case pilot. No large-scale unverified synthetic generation as the primary dataset.
**Reason:** A noisy label set makes every downstream metric unreliable — you can't tell a method failure from a label error. 170 clean examples support a defensible claim; 5,000 LLM-generated ones don't, unless explicitly labeled as synthetic and validated.
**Alternatives considered:** Fully synthetic dataset generated by an LLM for scale. Rejected as the *primary* set — may be used later as a clearly-labeled supplementary split, never as gold-standard test data.
**Risk if wrong:** Underpowered statistics; mitigated by using paired comparisons and reporting confidence intervals honestly rather than overclaiming significance.

### 1.4 LLM output is never trusted as its own verifier
**Decision:** The generator may *propose* a claim status (e.g., "SUPPORTED"), but the verification service independently re-evaluates every claim against the actual cited passage text. The generator's self-assessment is discarded, not merged.
**Reason:** Models are known to rationalize and mis-cite. If the same call that invents a claim also grades it, verification is theater. Independent verification is the entire research contribution — without it, this is just RAG with extra JSON fields.
**How to apply:** `verification/evidence_checker.py` must take `(claim_text, evidence_passage)` and produce its own SUPPORTED / CONTRADICTED / INSUFFICIENT_EVIDENCE — never read `claims[i].status` from the generator as ground truth.

### 1.5 Evidence IDs are never invented by the model
**Decision:** Only evidence IDs that were actually returned by the retrieval stage for that request are valid. Any claim citing an ID retrieval didn't return is treated as a validation failure (CONTRADICTED/INSUFFICIENT, never SUPPORTED by default).
**Reason:** Without this, the model can hallucinate a plausible-looking `DOC-014` and have it slip through as if it were grounded. Closing this loophole is cheap (a set-membership check) and is one of the few checks that *fully* eliminates a failure mode rather than just reducing its rate.

### 1.6 Compatibility is explicitly three-valued: compatible / incompatible / unknown
**Decision:** Version compatibility is never forced into a binary. "Unknown" is a first-class, distinct state from "compatible," and is never silently treated as compatible.
**Reason:** Most real documentation doesn't state compatibility explicitly. Forcing a binary either discards usable evidence (false incompatible) or quietly recommends version-unsafe fixes (false compatible). Preserving "unknown" is what lets the abstention layer behave honestly.
**How to apply:** `version_filter.py` must emit one of `{compatible, incompatible, unknown}` per passage, never infer compatibility purely from publication date.

### 1.7 Conflicting evidence is preserved, not resolved by similarity score
**Decision:** When two passages disagree, both are kept and explicitly labeled as conflicting; the system does not silently pick the higher-similarity one.
**Reason:** Picking the "winner" by cosine similarity throws away exactly the information (a deprecation, a behavior change between versions) that explains *why* a fix stopped working. Conflict is often the answer, not noise to remove.

### 1.8 Three-way decision: ANSWER / QUALIFY / ABSTAIN
**Decision:** The system never has only "answer" and "fail" — there's a middle state (qualified answer, with stated caveats) and an abstention path with an explicit reason.
**Reason:** Binary answer/no-answer forces overconfidence (if it must answer) or uselessness (if it's too conservative). The whole research hypothesis is about this middle ground, so collapsing it would erase the thing being measured.
**How to apply:** UI must render all three states distinctly (see [frontend.md](frontend.md)) — no green checkmark just because JSON parsed correctly.

### 1.9 No fine-tuning, no agent frameworks, no premature infra
**Decision:** Use one configurable hosted LLM via plain API calls. No fine-tuning, no multi-agent orchestration framework (LangChain-agent-style, AutoGPT-style), no Docker/Kubernetes, no paid vector DB, in the initial build.
**Reason:** These add surface area and cost without being necessary to test the core hypothesis (retrieval + verification, not model customization or agentic autonomy). Docker may be added later purely for reproducibility packaging, not as an architectural dependency.
**Risk if wrong:** None significant — all of these are addable later without redesigning the pipeline, since retrieval/generation/verification are already modular.

### 1.10 The AI service must run independently of the web stack
**Decision:** `ai-service/` (FastAPI) must be fully callable by evaluation scripts in `research/scripts/` without Express or MongoDB running.
**Reason:** Research experiments (B0–B5, ablations) need to run in batch, repeatably, without spinning up the full web stack or writing to a user-facing database. Coupling evaluation to the web app would make experiments slow, stateful, and hard to reproduce.
**How to apply:** `pipeline.py` takes a case dict in, returns a structured result dict out — no HTTP, no DB access inside the core pipeline function itself. FastAPI routes and eval scripts both call the same function.

### 1.11 Comparisons are fair by construction
**Decision:** All of B0–B5 run on the identical frozen test set with the same generator model/config, and predictions are saved once, then scored from the saved files — not re-generated every time metrics change.
**Reason:** This is the single most common way portfolio/research RAG projects quietly cheat themselves: re-prompting until numbers look good is p-hacking. Saving predictions first and scoring second makes that structurally impossible.

### 1.12 Control API spend explicitly
**Decision:** Pilot on a small case count first, cache repeated calls, log token usage per call, and cap generation+verification calls per run.
**Reason:** Two-stage generation+verification roughly doubles LLM calls per case versus a naive baseline; multiplied across B0–B5 and ablations across 150–250 cases, uncapped spend is a real risk.

### 1.13 Failure is shown, not hidden, in the UI
**Decision:** Unsupported claims, incompatible/conflicting evidence, and abstentions are rendered as clearly as successful answers — never a generic green "success" badge just because the response was valid JSON.
**Reason:** The research point of the whole project is honest uncertainty communication. A UI that hides it undermines the thing being built. See [frontend.md](frontend.md) for the specific status states.

### 1.14 Retrieved content is untrusted data
**Decision:** Documentation text, issue discussions, and code comments pulled into context are treated as data to reason over, never as instructions to follow, during generation and verification.
**Reason:** Prompt-injection via a retrieved GitHub issue ("ignore previous instructions...") is a realistic risk once real-world corpora (issues, discussions) are included. Treating retrieved text as inert data closes this off at the prompt-construction layer.

## 2. Key technology choices

| Layer | Technology | Why this, not an alternative |
|---|---|---|
| Frontend | React + Vite | Fast dev loop, component model fits the panel-based UI (evidence, claims, status) naturally. Vite over CRA for speed; CRA is effectively unmaintained. |
| Frontend language | JS (TS if time allows) | TS is preferred for the structured claim/evidence contracts, but JS is acceptable to not block early milestones on tooling. Revisit once contracts stabilize. |
| App backend | Node.js + Express | Thin orchestration layer: validates input, forwards to the AI service, persists sessions. Express is the lowest-ceremony choice for a REST gateway — no need for Nest's DI overhead at this scale. |
| App DB | MongoDB + Mongoose | Debug sessions and experiment metadata are naturally document-shaped (nested claims/evidence arrays, variable schema across experiment configs). Avoids a rigid relational schema for data that will change shape during research iteration. |
| AI service | Python + FastAPI | Python is non-negotiable for the retrieval/ML stack (sentence-transformers, FAISS, scikit-learn). FastAPI over Flask for native Pydantic validation — critical since the generator's structured output *must* be schema-validated and malformed responses rejected (see §1.4). |
| Output validation | Pydantic | The generator's JSON (diagnosis, claims, evidence_ids, decision) is exactly the kind of untrusted, model-produced structure Pydantic exists for — reject malformed output rather than trying to repair it. |
| Keyword retrieval | BM25 | Debugging questions contain exact tokens (error strings, package names, API names, version numbers) that dense embeddings routinely under-weight. BM25 is the cheap, reliable complement. |
| Dense retrieval | sentence-transformers + FAISS | Local, free, no paid vector DB dependency, sufficient for a corpus of this size (hundreds to low thousands of chunks). |
| Hybrid merge | Reciprocal rank fusion | Simple, parameter-light way to merge two ranked lists without needing a learned re-ranker — appropriate given the dataset size and time budget. |
| LLM | One configurable hosted API | Keeps a swappable interface (so model can change) without the complexity of a multi-provider abstraction layer the project doesn't need yet. |
| Testing | pytest (AI service), standard JS test runner (backend) | Matches each ecosystem's default rather than introducing a cross-stack test tool. |
| Experiment storage | JSONL/CSV + YAML configs | Human-diffable, git-friendly, no DB dependency for research artifacts — a prediction file and a config file should be reproducible from git history alone. |

## 3. What / How / Why — quick orientation

**What is FixTrace-RAG?**
A retrieval-augmented debugging assistant that, given an error + target library version, retrieves versioned documentation, proposes a diagnosis/fix, breaks the proposal into checkable claims, independently verifies each claim against the retrieved evidence, and then answers, qualifies, or abstains — rather than always answering confidently.

**How does it work, end to end?**
Error/version/code in → BM25 + dense retrieval over versioned docs → RRF merge + dedup → version-compatibility filtering (keeping "unknown" and conflicts visible) → LLM generates diagnosis/fix/claims/evidence-IDs → independent verifier re-checks each claim against the actual passage text (never trusting the model's own SUPPORTED label, never accepting invented evidence IDs) → decision layer picks ANSWER/QUALIFY/ABSTAIN → structured response flows back through Express to React, which renders evidence, claims, and uncertainty honestly.

**Why build it this way instead of a simpler chatbot-with-sources?**
Because "has a source" and "is actually supported by that source" are different claims, and most RAG debugging tools conflate them. The research bet is that making verification independent and version-awareness explicit measurably reduces confidently-wrong answers — and the project is designed to prove or disprove that bet on a fixed test set, not just to assume it.

**Why three services (React/Express/FastAPI) instead of one Python app?**
Portfolio value (demonstrates full-stack + ML systems skill) plus a real architectural reason: the AI/eval logic needs to run headless for batch experiments (§1.10), and a Node gateway is a natural place for session/auth/rate-limiting concerns that shouldn't live inside the research codebase.

**Why might this fail, and how would we know?**
If verification adds latency/cost without moving unsupported-recommendation-rate down, or if abstention tanks coverage more than it improves support rate, B4/B5 will simply score worse than B2/B3 on the frozen metrics — and that negative result gets reported, not hidden (§1.2).

## 4. Resolved decisions

### 4.1 Pilot corpus: Pydantic + SQLAlchemy
**Decision:** The pilot (and initial full) dataset is built around two Python libraries: **Pydantic** and **SQLAlchemy**.
**Reason:** Both have well-documented, high-impact breaking changes across major versions — Pydantic v1→v2 changed validation/config semantics extensively; SQLAlchemy 1.x→2.x changed core query/session APIs. Both projects maintain clean, versioned documentation (readthedocs/official docs per release), which is exactly the kind of source material the version-filter and compatibility-labeling logic needs. This beats NumPy/Pandas (more incremental deprecation, fewer hard version splits) for generating genuine version-conflict cases, and beats LangChain (faster-moving but messier/less stable docs, higher corpus-cleaning cost for the time budget).
**How to apply:** `research/configs/*.yaml` list `corpus.libraries: [pydantic, sqlalchemy]`. Ingestion (`ai-service/app/ingestion/`) should start with official docs + changelogs/migration guides for both libraries' major versions.

### 4.2 LLM provider: Anthropic Claude API
**Decision:** Generation and verification both use the Anthropic Claude API (`ANTHROPIC_API_KEY`, default model `claude-sonnet-5-5` per `.env.example`).
**Reason:** Keeps the whole project on one vendor for the eventual write-up (simpler cost/latency accounting, one client library), and Claude's structured-output reliability is sufficient for the diagnosis/claims/evidence-IDs contract in `schemas.py`.
**How to apply:** `ai-service/app/config.py` reads `ANTHROPIC_API_KEY`/`LLM_MODEL` from env. If a second provider is ever needed for a planned comparison (not for routine use — see §1.12 on avoiding unnecessary multi-model spend), it's an explicit ablation, not a silent swap.

## 6. Implementation status

What's actually scaffolded and running as of this writing (update this section as real pipeline code lands — don't let it drift from git history):

- `ai-service/`: FastAPI app with `/health` and `/config` only. `schemas.py` defines the full contract (`DebugRequest`, `EvidencePassage`, `GeneratedClaim`, `VerifiedClaim`, `DebugResponse`). Retrieval/generation/verification modules are not yet implemented — `ai-service/app/{ingestion,retrieval,generation,verification}/` are empty directories.
- `backend/`: Express app with `/api/health` only, tested with Jest+Supertest. No `/api/debug` forwarding yet, no MongoDB models yet.
- `frontend/`: Vite+React scaffold with a single `DebugPage` that confirms backend connectivity. None of `DebugForm`/`DiagnosisPanel`/`EvidencePanel`/`ClaimVerification`/`StatusBadge` exist yet — intentionally deferred until there's a real `/api/debug` response shape to render.
- `research/`: config YAMLs for B1/B2/B3/B5 exist and encode the decisions above. No corpus, no scripts, no predictions yet.
- CI (`.github/workflows/tests.yml`) runs `ai-service` pytest and `backend` Jest on push/PR.

Next concrete step: build the pilot corpus (`research/data/raw/`) for Pydantic + SQLAlchemy, then `ai-service/app/ingestion/` (loaders + heading-based chunking + metadata), then BM25/dense retrieval — i.e., start of Milestone 2.
